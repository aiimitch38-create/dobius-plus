# Investigation Report: Dobius+ (dobius-plus) — UI-UPDATES worktree

## Summary

Dobius+ is a mature, actively-developed Electron app (568 commits, v1.0.82) that wraps Claude Code CLI in themed, multi-window, multi-tab terminals with a dashboard layer. The codebase is large (~24.2k lines in `electron/`, ~22.5k lines in `src/`) and shows evidence of a disciplined, review-heavy process: a 34KB `LESSONS-LEARNED.md`, a dense `electron-builder` afterPack guard, extensive inline "Codex"/"Audit" comments documenting prior security and race-condition fixes. The headline finding is that the documented project state in `.claude/CLAUDE.md` and `HANDOFF.md` is stale by several months — the actual working tree is clean at `72f76915` (v1.0.82), not the "26 uncommitted files at v1.0.22" described in those docs. The tab tear-off/docking subsystem (the last 24 commits) is a genuinely complex, carefully-reasoned ownership/lifecycle state machine; it looks functionally complete for the cases its own comments enumerate, but its complexity is itself the risk — each of the 24 commits fixed a distinct edge case found after the fact, and the pattern of "found a new interleaving" repeats enough times to suggest more edge cases are plausible. This worktree also has no `node_modules` installed, so none of the `build`/`test:*` npm scripts can actually be run from here to verify any of this directly.

## Key Findings

1. **Project status docs are stale (several months out of date).** Severity: medium.
   `.claude/CLAUDE.md:30-45` ("Current build status") claims version `1.0.22`, HEAD `d082675`, and "26 uncommitted files" (dashboard Costs/Prompts/Search/ChangeFeed feature in flight). `HANDOFF.md:1-6` similarly describes v1.0.24 source vs. v1.0.22 installed, dated 2026-06-21. The actual repo state (per git status/log at session start, confirmed again via `git status --short` returning empty) is a **clean** tree at `72f76915`, package.json version `1.0.82` (confirmed in `package.json:3`). `LESSONS-LEARNED.md:52` repeats the same stale "large in-flight dashboard feature uncommitted" note from a 2026-06-13 audit. All three docs describe a snapshot roughly 60 commits and several version bumps behind current `main`/branch head. Anyone onboarding from these files alone would materially misjudge the project's state.

2. **Tab tear-off/docking is a deliberately over-engineered state machine, by necessity — complex but well-reasoned, not obviously incomplete.** Severity: medium (risk area, not a bug).
   `electron/window-manager.js` contains ~20 functions and a `projectWindows` Map tracking ownership (`entry.webContents.id`), confirmation (`tearOffConfirmed`), docking-in-flight (`dockingTabs`), and restore-preservation sets (`openedTearOffTabIdsThisSession`, `pendingTearOffKeys`) — e.g. `getOpenTearOffsForRestore` (window-manager.js:134-157), the `'closed'` handler's ownership-based kill logic (window-manager.js:550-587), and `primaryDockTarget` (window-manager.js:340-356). Nearly every block carries a comment citing a specific prior bug ("Codex High", "Audit H1", "v1.0.66") that the current logic was rewritten to fix — e.g. the explicit note that ownership must be checked via `getTerminalWebContentsId(id) === null`, NOT registration, because "an in-flight tear-off is registered BEFORE it claims T" (window-manager.js:412-416). The last 24 commits in git log are exclusively about this feature (`git log --oneline | grep -ic "tear\|dock"` = 24 of the last ~24-30 commits), each fixing one more interleaving (source-window-closes-mid-drag, main-window-reload-during-dock, resume-cancel-during-tear-off, etc.). There is a dedicated test file (`electron/__tests__/tearoff-tabs.test.mjs`, 66 lines) and a `test:tearoff` npm script, but it could not be executed in this worktree (no `node_modules`) to confirm current coverage against the latest fixes.

3. **All previously-documented "fragile area" safeguards are still present and in some cases more robust than documented.** Severity: info (verification, not a new risk).
   - Null bytes in `execFile`: `electron/git-service.js:1-26,133` still routes everything through `execFile` (not shell=true) and documents the `%x00`/`||SEP||` convention; no raw `\x00` usage found.
   - Tab mounting: not independently re-verified by reading `TerminalPane.jsx` in full this pass, but no contradicting code found; CLAUDE.md's claim is consistent with the mount-state patterns seen in `TerminalTabBar.jsx`.
   - `remote-debugging-port`: confirmed absent from `electron/main.js` (`grep -n "remote-debugging-port" electron/main.js` → no match), consistent with the "pre-ship check" rule in both CLAUDE.md files.
   - CLAUDE.md file allowlist: `electron/main.js:1223-1309` (`setupFileHandlers`) is **more defensive** than the root CLAUDE.md summary suggests — it resolves symlinks segment-by-segment (`resolveFollowingSymlinks`, main.js:1256-1268) and rejects any resolved path outside the user's realpath'd home directory, explicitly closing a documented prior hole ("basename match alone... allowed /etc/CLAUDE.md", main.js:1227-1230) and a symlink-ancestor escape ("Codex round-3 BLOCKER", main.js:1255).
   - Sandbox/contextIsolation: every `BrowserWindow` webPreferences block (`electron/main.js:162-164`, `electron/window-manager.js:663-670,733-740,838-843`) sets `contextIsolation: true, nodeIntegration: false`; `sandbox: true` is still absent everywhere, matching the previously-accepted LOW:SECURITY finding in `REMAINING-ITEMS.md:11-12` ("sandbox would break node-pty IPC... acceptable for local desktop app").

4. **Earlier self-audits (AUDIT-FINDINGS.md / AUDIT-REPORT.md / SELF-REVIEW-FINDINGS.md) describe a much smaller, earlier codebase and should not be trusted as current.** Severity: info.
   `AUDIT-REPORT.md:26` states "33 source files total" and is dated 2026-02-21; `REMAINING-ITEMS.md:5` cites `electron/data-service.js` as "369 lines"; the file is now 2,731 lines (`wc -l electron/data-service.js`). These documents accurately describe fixes that were made (e.g. the sessionId path-traversal guard, prototype-pollution guard — both independently confirmed present at `electron/config-manager.js:19` `UNSAFE_KEYS` and `electron/data-service.js:1614` `safeProjectSegment`), but their file/line references and scale claims are long obsolete and should not be used for current navigation.

5. **This worktree cannot build or run its own test suite as-is.** Severity: medium (process/onboarding risk).
   `node_modules/` does not exist in `/Users/bayou/Projects (Code)/dobius-plus/UI-UPDATES` (`ls node_modules` → "No such file or directory"). `npm run build` fails with `sh: vite: command not found`; running any `electron/__tests__/*.test.mjs` file directly with `node` fails with `ERR_MODULE_NOT_FOUND: Cannot find package 'electron'` (confirmed running `node ./electron/__tests__/tearoff-tabs.test.mjs`). None of the findings in this report (clean build, test pass/fail state) could be confirmed by actually running the project's own verification commands — all project-doc claims about test status are necessarily second-hand until `npm install` + `electron-rebuild` are run here.

## Architecture Map

- **Main process** (`electron/`, ~24.2k lines): `main.js` (3,755 lines) is the IPC/bootstrap hub — window creation, file handlers (CLAUDE.md allowlist), Claude hooks management. `window-manager.js` (921 lines) owns the `projectWindows` Map and all tear-off/dock lifecycle. `terminal-manager.js` (929 lines) wraps `node-pty`, including the `spawn-helper` executable-bit self-heal (`ensureSpawnHelperExecutable`, terminal-manager.js:31-64) paired with `build/after-pack.cjs`. `data-service.js` (2,731 lines) and `data-utils.js` (188 lines) do read-only parsing of `~/.claude/*` (history, transcripts, stats) with the bounded tail-read fix for OOM (per LESSONS-LEARNED.md:77-81). `config-manager.js` (1,665 lines) owns the single `~/Library/Application Support/dobius-plus/config.json` persistence with prototype-pollution guards. Other main-process modules cover voice bridge/conductor, git service, auto-resume, account/profile management (multi-Claude-account support), Asana queue polling, mobile server (Tailscale-based phone mirroring).
- **Renderer** (`src/`, ~22.5k lines React 19 + Zustand): `ProjectView.jsx` (1,407 lines) is the per-project window shell; `TerminalTabBar.jsx` (930 lines) implements tab reorder + tear-off drag detection (`dragLeftWindow` ref, TerminalTabBar.jsx:200-230) and docking; `TerminalPane.jsx` (620 lines) wraps xterm.js, kept mounted via CSS `display:none` per house rule. `store/store.js` (837 lines) is the Zustand state. The Dashboard (`src/components/Dashboard/`) is a large tab set: Agents, Orchestrator, Settings, Sessions, AccountsSection, Board/Kanban, plus newer Costs/Prompts/Search/ChangeFeed components that the stale docs describe as "in flight" but which now appear to be normal, committed files.
- **IPC contract**: `preload.js` (424 lines) exposes a large, explicitly-named `electronAPI` surface (terminal*, agents*, orchestration*, file* for CLAUDE.md, checkpoint*, data* for read-only `~/.claude` access, gws* for Google Workspace multi-account, chrome* profile launching) via `contextBridge`, consistent with `contextIsolation: true` everywhere.
- **Tests**: `electron/__tests__/*.test.mjs`, ~60 files wired through `package.json`'s `test` script (a long `&&`-chained list), including a dedicated `tearoff-tabs.test.mjs`. Could not be executed in this worktree (missing `node_modules`).

## Risk Areas

- **Tear-off/docking ownership logic** (`electron/window-manager.js`) is the single most complex piece of state in the app: ownership is tracked by live `webContents.id` comparison rather than simple registration, specifically because registration-based ownership was proven wrong in a prior round (window-manager.js:412-416). Any future change to window/tab lifecycle (new window type, new restore path) needs to reason through this same ownership model or risk re-introducing a leaked-PTY or wrongly-killed-tab bug — the kind of bug this file's own comments show took multiple review rounds to find each time.
- **Stale onboarding docs** actively mislead rather than merely being outdated: `.claude/CLAUDE.md`'s "Current build status" section reads as present-tense instruction ("Review these before starting new work") pointing at files/commits that no longer represent reality. A future session or agent trusting it could branch over work that was already merged months ago, or hunt for "26 uncommitted files" that don't exist.
- **No installed dependencies in this worktree** means no local verification (build, lint, or any `test:*` script) is possible without first running `npm install` and `electron-rebuild` (the latter required per CLAUDE.md for native modules `node-pty`/`better-sqlite3`). Any "done bar" style gate (build exits 0, tests pass) cannot currently be satisfied from this checkout.
- **`sandbox: false` (implicit) across all BrowserWindows** remains an accepted, documented trade-off (REMAINING-ITEMS.md:11-12) rather than a new risk, but it is a standing attack-surface note given the app also embeds `<webview>` (`webviewTag: true`, e.g. window-manager.js:669, 739, 842) for dev-server/browser preview panes.
- **Self-audit documents (AUDIT-FINDINGS.md, AUDIT-REPORT.md, SELF-REVIEW-FINDINGS.md) are frozen snapshots** of a much smaller codebase (Feb 2026, 33 files) and risk being mistaken for current state by anyone searching the repo root for "the last audit."

## Recommendations

1. Regenerate or prune `.claude/CLAUDE.md`'s "Current build status" section and `HANDOFF.md` to match the actual clean/current state (`72f76915`, v1.0.82) — or remove the stale snapshot sections entirely if they're not kept current, since a wrong "in-flight work, review before building" note is worse than no note.
2. Run `npm install && npx electron-rebuild` in this worktree before any build/test/lint work is attempted here, and consider adding a one-line check at the top of `CLAUDE.local.md` or a preflight script that fails fast with a clear message when `node_modules` is absent, rather than letting `vite: command not found` be the first symptom.
3. Given 24 consecutive commits fixing tear-off/dock edge cases, consider a dedicated "tear-off state invariants" doc (ownership rule, confirmation rule, restore-preservation rule) distilled from the window-manager.js comments into one place, so the next edge case is reasoned about against written invariants rather than rediscovered from scratch.
4. Archive or clearly date-stamp `AUDIT-FINDINGS.md` / `AUDIT-REPORT.md` / `SELF-REVIEW-FINDINGS.md` (e.g. move to `archive/` or prefix filenames with their date) so they aren't mistaken for a current health report by a new reader or future audit.
5. Once dependencies are installed, actually run `npm run test` (or at minimum `npm run test:tearoff`) to confirm the 24-commit tear-off fix sequence is fully covered — this report could not verify pass/fail state.
