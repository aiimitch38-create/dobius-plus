## Finding

The requested persistent *personal account* connection is technically possible through Telegram’s user MTProto API. The current Hermes Telegram adapter and Dobius Telegram destination do not implement it: Hermes uses a Bot API token, while Dobius’ destination sends with `/bot<TOKEN>/sendMessage`. There is no source-supported Settings toggle that can attach a personal account today.

The existing Hermes HTTP session/run API is not a safe attachment point for the current interactive Adam process. It creates a fresh API-server `AIAgent`; its `session_id` supports transcript/session correlation, not a live-runtime attachment or shared single-owner lease. The smallest coherent implementation is a **Telegram personal-client platform adapter inside Adam’s already-owned Hermes `GatewayRunner`**, feeding structured messages into the gateway’s existing `MessageEvent` pipeline. This adds a Telegram client to the existing Adam profile/gateway; it must not create a second Hermes head or treat the current CLI/PTY session as attachable. Until that adapter, policy gates, and consent process exist, the correct state is disconnected.

## Primary Telegram constraints

Telegram’s current API terms prohibit using platform data to develop, enhance, or deploy AI systems by default. The content-licensing terms describe only a possible exception when **all relevant users individually provide explicit, informed, affirmative, continued consent**, limited to specific content and a specific chat/context; consent from one chat does not transfer to another. They say exceptions *may* be granted, so implementation should remain disabled until the permitted basis is confirmed and the consent requirement is actually met. ([Telegram API Terms §1.5](https://core.telegram.org/api/terms), [Terms of Service for Content Licensing](https://telegram.org/tos/content-licensing))

Telegram also requires the client developer to obtain its own `api_id` and make users aware that the app uses Telegram’s API. The supported user authorization flow is a real Telegram client authorization associated with an MTProto auth key; Telegram documents code/2FA and QR/passkey options. A durable authorization means no routine browser login, but revocation, expiry, or session invalidation can still require a user-mediated reauthorization. ([Creating your Telegram Application](https://core.telegram.org/api/obtaining_api_id), [User Authorization](https://core.telegram.org/api/auth))

Additional relevant requirements:

- Telegram forbids acting on the user’s behalf without their knowledge and consent (API Terms §1.4). Outbound replies therefore need an explicit, visible send policy and revocation path; account connection alone must not imply permission for arbitrary sends.
- Telegram update delivery is connection-sensitive; clients must persist and reconcile `seq`, common `pts`/`qts`, and per-channel `pts` state, ignore duplicates, and fill gaps. Telegram documents bounded update history and a `differenceTooLong` case, so recovery cannot promise unlimited historical replay. ([Working with Updates](https://core.telegram.org/api/updates))
- MTProto `messages.sendMessage` requires a unique `random_id` to prevent resending. A durable application outbox should reuse the same ID for a retry of one logical send. ([messages.sendMessage](https://core.telegram.org/method/messages.sendMessage))
- Telegram’s official TDLib is a cross-platform, full client library that handles encryption, storage and ordered updates; its local data is encrypted using a user-provided key. That makes it the best-supported first implementation candidate, with the key protected by the OS credential store. GramJS is not a Telegram-owned API/library source in this review, so I do not recommend it over TDLib without a separate maintenance/security review. ([TDLib](https://core.telegram.org/tdlib))

## Concrete implementation contract

**Owner:** the already-running Hermes Adam `GatewayRunner` profile owns one personal Telegram adapter instance. Dobius Settings > Agents should only configure/observe this connection via a narrow authenticated local control API; it must not run a second Hermes process, pass auth material on argv, or provide a generic shell/terminal injection path. If “existing Adam” means an interactive CLI/PTY process rather than the profile’s gateway, no supported API attaches Telegram messages to that live process; implementation must target the profile’s single GatewayRunner owner instead.

**Candidate API boundary (proposal, not implemented):**

```text
PersonalTelegramAdapter.start(accountRef, exactlyThreeChatGrants, policy)
PersonalTelegramAdapter.stop()
PersonalTelegramAdapter.status() -> { connected, accountDisplayId, allowedChatCount, lastUpdateAt, errorCode }
onInbound(event: TelegramInboundEnvelope) -> durable accepted/rejected receipt

TelegramInboundEnvelope = {
  connectionId, generation,
  peerId, senderId, messageId, updateCursor,
  threadId?, eventKind, boundedText?, boundedMediaRefs?, sentAt
}
```

1. **Enrollment/auth:** Dobius Settings > Agents chooses existing Hermes Adam and opens a one-time local TDLib authorization UI (QR/code/2FA as Telegram requires). Obtain/register the app’s own `api_id`; store the `api_hash` and TDLib encryption key in OS-protected credential storage, and keep TDLib database files private/encrypted. UI should display the connected account identity and explain that Telegram content is sent to the configured AI service. No plaintext login codes, auth keys, hashes, or transcripts in config, argv, logs, or reports.
2. **One connector owner:** instantiate the adapter only in the existing Adam profile GatewayRunner. Acquire a machine-local lock keyed by stable Telegram user ID with process start/instance UUID, and refuse a second Adam connector. This only arbitrates this Dobius/Hermes installation; do not claim it disables Telegram sessions on other devices. On reconnect use TDLib’s persisted update state; surface gaps/too-old cursor as a visible “needs review/resync” condition rather than silently skipping old messages.
3. **Exactly three chats:** the authenticated account owner selects exactly three allowed group/supergroup peer IDs in the UI. Persist stable numeric IDs, not titles/user-entered names, and verify each observed update’s account, peer, event kind, sender, and configured membership before accepting it. Reject other peers, channels unless explicitly supported, outgoing self-messages, service events, and unsupported media by default.
4. **Consent and provenance:** record per `peerId × participantId` individual explicit/informed/affirmative/continued consent, with policy/version, capture time, scope, and revocation state. Keep messages disabled for AI routing unless every relevant participant in that exact chat has a valid consent record and the applicable Telegram exception/permission is confirmed. Revalidate on each inbound update and immediately before model dispatch; revoke pauses ingestion and purges or quarantines retained Telegram-derived content according to the approved policy. Do not treat user account ownership, group membership, or admin status as the other participants’ consent.
5. **Bounded structured ingress:** translate accepted updates to `MessageEvent` and call the existing `GatewayRunner._handle_message` path in-process. Add a separate `telegram_personal` platform/account namespace in the session-key builder so personal-account and bot sessions cannot collide. Default to sender-isolated group sessions; never join all three groups to the Adam CLI transcript. Use the existing active-session guard and a strict platform tool policy. Since group text is untrusted, disable terminal/shell, arbitrary file access, network tools, and autonomous actions for this connector unless a separately reviewed approval flow explicitly grants an action. No raw message becomes a terminal command.
6. **Cursor and idempotency:** persist a durable inbox unique key such as `(accountUserId, peerId, messageId, editVersion)` plus TDLib update state. Atomically save an accepted event and its cursor before acknowledging application-level consumption; dispatch it once through a session queue. If delivery outcome is ambiguous, consult that receipt and never create a second agent turn just because a network timeout occurred. Use a stable per-send outbox action ID and MTProto `random_id` for duplicate-safe outbound retry. Treat TDLib server-side update retention as finite; any `differenceTooLong` or unrecoverable gap must be surfaced, not hidden.
7. **Outbound boundary:** default to replies disabled until a visible, user-selected policy is established. For allowed replies, bind destination peer to the same one of the three configured chats, apply a length/media allowlist, and use `random_id` plus durable send receipts; no arbitrary tool can message any Telegram peer. Provide immediate disconnect/revoke, lock release, and UI status. Reconnecting must not replay already committed inbox receipts or repeat sends.

This extends Hermes’ current adapter contract (`connect`/`disconnect`, `send_message`, `on_message`) rather than misusing its bot-token adapter. It does require code in Hermes gateway (platform adapter, account auth/session backend, account lock, durable update/inbox handling and per-platform tool policy) plus Dobius Settings UI/preload/main-process control and secure credential storage. There is no evidence in current Dobius destination code that it already supplies such a control API. First implementation should be a disconnected synthetic adapter and fixtures: fake TDLib updates for the three allowed peers and an unapproved fourth peer; authorization revoke and per-participant consent revoke; update cursor duplicate/gap/too-old; restart replay; concurrent second owner refusal; same-chat same-message replay produces one run; same numeric peer under bot vs personal platform gets different session IDs; untrusted text cannot invoke terminal/network tools; and duplicate outbound `random_id` retry. Only after those pass should a separate user-mediated auth and three-group enrollment be considered.

## Remaining proof and limits

- Source proves the current adapter/destination are bot-token integrations and the API server provides structured but non-attaching API runs. **No live Hermes process, connected Telegram account, API server, TDLib session, or Dobius UI state was inspected.** No login, session list, private group content, profile, or credential store was read.
- No tests were run: this was a bounded architecture/source audit, not implementation verification. No source changes were made.
- `api_id`/`api_hash` must be registered for this client; user authorization must happen once through Telegram’s supported flow. Whether it can use an existing approved client application ID is not established here.
- Telegram’s AI/content licensing restriction is a release blocker for group message-to-model forwarding until an applicable permission/exception and per-person consent path are established. This report does not decide legal applicability.
- The three group IDs, participant set, consent evidence, exact live Adam profile/gateway owner, secure TDLib package availability, OS credential storage, durable cursor DB, and message/tool retention policy remain unverified.
- No automatic sends, account linking, inference, or production enablement is authorized by this research.
