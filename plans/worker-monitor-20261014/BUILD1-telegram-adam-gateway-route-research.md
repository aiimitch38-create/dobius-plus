## Recommendation

**Use a Hermes gateway platform plugin as the transport adapter, with Dobius remaining the Telegram account/session and durable-consent owner.** The plugin platform registry, `BasePlatformAdapter` message handler, per-platform session keys, and adapter connect/disconnect lifecycle are actual supported extension points. This lets the gateway construct agents under the selected Adam Hermes profile and use that profile's provider/auth/runtime configuration. It is the smallest supported route for structured messages into Hermes' existing gateway dispatcher.

This route creates a distinct gateway conversation keyed by platform/chat/sender/thread; it does **not** attach Telegram to the currently open Adam CLI/TUI conversation or borrow its live AIAgent. Keeping the TUI open is compatible at the profile/configuration level if the plugin runs inside the existing Adam profile's single GatewayRunner. It must not start a second GatewayRunner against that profile. The TUI transcript and gateway session are separate owners/sessions. Same-profile, multi-process SQLite/config concurrency and how the UI should surface the gateway conversation remain explicit acceptance checks; no runtime was probed here.

A plugin platform's custom config **cannot prove a zero-tool or narrow tool allowlist**. Current toolset resolution admits automatically discovered plugin toolsets, non-configurable platform tools, context-engine tools, and globally enabled MCP servers; `PlatformEntry` has no immutable execution policy field. Even `platform_toolsets[platform] = []` is not a hard execution boundary. A dedicated untrusted Telegram platform therefore needs a small Hermes-core, host-enforced allowlist carried on the AIAgent and checked both after all tool schema injection and at execution. Plugin `pre_tool_call` hooks are useful defense-in-depth, not the authority: failures in the executor's hook call are caught and treated as no block.

The plugin route is **not ready to implement or enable** until Dobius has a production authenticated local transport/enrollment provider, durable event admission/reply receipts and a sender/chat consent policy, and Hermes accepts the hard tool-scope seam. The existing Dobius main-owned Adam principal registry and intent bridge are source foundations only: `createDefaultAdamCloudIntentBridge()` supplies `AdamServicePrincipalRegistry.unavailable()` until trusted peer/enrollment providers are composed. They do not authenticate a Hermes plugin process today.

## Smallest maintained implementation and ownership

1. **Dobius main (ROOT + Telegram service owner):** keep MTProto authorization, update normalization, exactly-three-chat enrollment, sender/chat consent, cursor and dedupe ledger, encrypted auth/session storage, and outbound MTProto sends in the existing main-owned Telegram service. Add one authenticated local bridge protocol with bounded schemas and request IDs. Enrollment/authentication must verify a real main-owned Hermes service principal/peer, not a same-user bearer, Telegram sender string, supplied profile name, or renderer value. The current `AdamServicePrincipalRegistry` can be evaluated as the identity authority, but its default bridge is deliberately unavailable until a trusted transport peer and enrollment provider exist. Do not publish credentials or raw MTProto/session material over the bridge.
2. **Hermes plugin owner:** add one `plugins/platforms/dobius_adam_telegram/` platform plugin with `plugin.yaml`, `__init__.py`, and adapter. Register via `PluginContext.register_platform`; connect only to Dobius' authenticated local bridge; convert verified, bounded receipts to `MessageEvent`; return delivery results only through the correlated bridge outbox. Declare an isolated platform identifier and no general HTTP listener. Bind the gateway session to verified peer/sender/thread metadata and source request ID. The plugin's `pre_gateway_dispatch` hook may reject unsupported event kinds as defense-in-depth, never as proof of process identity.
3. **Hermes gateway/agent owner:** add the minimum host-owned hard tool policy passed from trusted platform configuration to every GatewayRunner-created AIAgent. Apply it after registry tools, plugin tools, memory tools and context-engine tools are assembled, then check it again at the executor after Tool Search resolution and before dispatch. Propagate it to delegates/child agents and runtime helper paths. Do not rely on plugin `platform_toolsets` or fail-open `pre_tool_call` as the only control.
4. **One Adam profile owner:** use the already-approved Adam profile's existing gateway process if one exists, and register this adapter there. If none exists, start one profile-scoped gateway only after separate approval and lifecycle review. Do not start a second gateway against the same `HERMES_HOME`. The current TUI may stay open as a separate client, but the gateway uses its own platform/chat/sender session and cannot claim to be attached to or to own the live TUI conversation.

### Required deterministic source tests before any live behavior

- Platform plugin registration, factory/config validation, connect/disconnect, reconnect, and bounded event parsing with fake Dobius local bridge peers.
- Forged peer, missing/revoked principal, stale generation, replayed request ID with equal/different payload, wrong Telegram account generation, unapproved peer/sender, outgoing/service/media update, and no `internal=True` bypass.
- Same sender/message replay creates one gateway turn and one outbound receipt; ambiguous bridge response recovers by exact receipt without a second dispatch/send. Crash points before receipt commit, after commit/before event dispatch, after model completion/before reply receipt, and after reply receipt/before Telegram send acknowledgement.
- Cancellation races against event admission, active tool execution, completion and reconnect; cancellation is limited to the authenticated request/session generation and returns a terminal/ambiguous receipt, never falsely claiming the tool stopped.
- Assert final agent schemas and actual execution deny every non-allowlisted tool despite enabled plugin toolsets, MCP, memory/context-engine additions, Tool Search unwrap, delegates and stale cached agents. Include empty allowlist and policy lookup failure as fail-closed cases.
- A parallel TUI + same-profile GatewayRunner test (only if Hermes explicitly supports it) verifies SQLite integrity, no shared live agent, no history/session collision, and no duplicate gateway owner. This is not covered by source review.

## Decisions and unresolved proof

The user/product owner must decide whether Telegram messages should create a **separate Adam-profile gateway session** (recommended, sender-isolated by default) or whether exact live TUI transcript attachment is a hard requirement. The latter has no supported API in the inspected source and needs a new explicit session owner/correlation design; `/v1/runs` or an identical session ID does not provide it.

Before implementation/live use, ROOT must identify the one gateway owner/profile without reading private profile material in this review; provide an OS-backed local transport peer/enrollment implementation; determine cross-platform local IPC behavior; set the allowed tool names and delegated-task policy; define durable request/reply/cancellation receipt semantics; and obtain the separate Telegram consent/retention/outbound-policy decision. A profile name or `HERMES_HOME` path alone is not caller authentication. The review did not inspect active gateway processes, installed profile contents, service state, API/server listeners, credentials, group IDs/messages, or tool execution.

No source edits, tests, model/provider calls, Telegram/API login, network requests, gateway/model/tool execution, subscriptions, real messages, service actions, installs, restarts, Git mutation, profile/config/credential/keychain/head/session reads or writes occurred. AWS remains deferred and the historical Storage queue remains paused. This is a research recommendation only, not source, packaged, or live acceptance.
