## Finding

The reviewed coordinator is an in-process foundation only. RESEARCH's `integration-contract-review-20261014` (`CHANGES_REQUIRED_BEFORE_COMPOSITION`) identifies `LAYA-CROSS-PROCESS-FENCE`: a synchronous epoch recheck does not linearize against another process committing after the final async source reread and before journal/cache publication. RESEARCH separately passed the exact coordinator freeze as `PASS_BOUNDED_INTERNAL_FOUNDATION`, while stating that constructor-supplied participant IDs/readers cannot prove real writer coverage. Keep the all-surface reader unavailable until both writer participation and the publication critical section below are implemented and reviewed.

The existing mutation sources are not one transaction: cloud-jobs SQLite, JSON stores using `SafeJsonFile`/atomic rename, the data-catalog root lock, monitor-owned Python JSON files and lock, in-memory agent process/session state, and external files/OS permission state. The current monitor `InstanceLock` only excludes duplicate monitor instances. The root enrollment lock only serializes that registry file. Neither fences Laya publication or unrelated app instances.

## Smallest shared fence protocol to implement

Proposed fence metadata belongs in the existing authority-host `cloud-workstation/jobs.sqlite` database, not a second job/catalog database. If that database/authority host is absent, all-surface Laya stays unavailable. The table would be a lock/revision protocol only; source facts remain owned by their current stores. Do not create a separate competing database or treat the fence table as a source of job, task, permission, storage or file truth.

1. A participating synchronous writer acquires the shared SQLite `BEGIN IMMEDIATE` gate before any mutation becomes visible. A separate Node/Python connection uses the same private database file and a bounded zero/short busy timeout. Contention makes the caller fail closed/retry before the source write; it never waits indefinitely on Electron's main thread.
2. With the fence held, the writer acquires its source-local transaction/lock, rereads current state under that local boundary, performs the source update, writes its durable source revision, and advances the fence generation before committing. For a source in the same SQLite database, update source rows and generation in one transaction. For JSON, keep the global gate through atomic rename and revision publication; persist source revision in the same versioned document where possible. Always release local lock/transaction before releasing the outer fence.
3. No asynchronous callback, provider call, filesystem scan, UI/RPC wait or child-process wait is allowed while holding the fence. Work that needs awaits occurs before the final synchronous revalidation; if the source can change while waiting, it must be reread under the fence or refused.
4. Advisory admission captures a ticket and the source revision vector while serialized by the fence, then releases it before any provider/network work. After provider completion, do not rely on `current()` then append: the final operation must reacquire the shared gate, compare the exact captured epoch and every source revision, recheck required deployment/evidence identity, append the audit decision and update the in-memory suggestion/cache in one synchronous publication callback, then release. A source writer cannot commit between this check and suggestion publication.
5. Service API must gain a publication primitive (for example `publishIfCurrent(ticket, synchronousCommit)`); the current `LayaAdvisoryService` only performs a scalar epoch read before synchronous journal/cache writes, so its present API cannot provide this linearization. Cache-hit delivery also needs the same fenced final check; otherwise a writer can change authority after cache validation but before returning the cached suggestion. The provider's check adjacent to `fetch` remains a request-send check, not the final result publication fence.
6. Journal atomicity needs explicit treatment. The existing Laya journal appends/fsyncs JSONL under its own `LayaAdvisoryJournalLock` directory lock, separate from SQLite. The required lock order is shared fence then journal lock; no code holding the journal lock may acquire the shared fence. If the journal append succeeds but the fence transaction fails/crashes, that line must not be projected as a committed/current suggestion. Implement a committed-publication marker keyed by decision ID and require journal readers/projections to filter through it, or move journal append and publication marker into the same existing SQLite transaction. Until one of these is implemented, the final publication gate remains unavailable; do not claim atomic fence+JSONL commit.
7. Start-up only opens the reader after bounded reconciliation under the same fence: validate the existing source revision manifest against every participant's durable revision, detect a crash between a JSON rename and fence generation update, verify journal commit markers, reconcile worker/agent process identities, and ensure no source lock or unresolved write remains. Missing, malformed, changed-without-revision, or ambiguous state leaves reader unavailable. A PID timeout, timestamp, lock-file age, empty ledger, or successful service restart is not proof to clear a pending writer.

A `BEGIN IMMEDIATE` transaction lock is released by SQLite when a process exits, unlike an app-created lock directory that can remain stale. Nevertheless, a crash after an external file rename and before its shared revision transaction commits creates a detectable source/manifest mismatch; startup must detect that mismatch and fail closed/reconcile before advancing. Every JSON source therefore needs a durable revision (or a bounded content digest of the complete authority document) that can be read while the shared lock is held. Files whose authoritative content cannot be synchronously/fully revalidated do not qualify as participants.

## Lock order and crash rules

Canonical order for a writer is: shared `jobs.sqlite` fence → that source's local transaction/lock → synchronous write and durable revision → local lock release → shared fence generation commit/release. A same-database writer uses one transaction, not a nested `BEGIN IMMEDIATE`. Root enrollment uses the shared fence before `withRootEnrollmentWrite`; the monitor's process-singleton `monitor.lock` remains outer-only and is never acquired while holding the shared fence. Publication order is: shared fence → Laya journal lock → append/commit marker/cache result → release journal lock → release shared fence. No reverse edge is allowed.

If a source mutation throws before changing state, release the gate and advance/invalidate conservatively; if it may have partially changed state, leave the participant unavailable until the source is reloaded and reconciled. A process crash releases SQLite's OS lock automatically, but startup still compares durable source revisions and checks outstanding attempt/run identity. A monitor child may remain alive after Electron exits; a new main process cannot assume it stopped. A stale journal lock directory is handled by the existing fail-closed behavior and is never removed by age/PID guess. The global protocol must not “repair” or unlink the catalog lock, monitor lock, or journal lock based on stale-looking metadata.

## Platform and scope limits

- SQLite's cross-process locking contract must be verified against the actual SQLite/Node build and Python stdlib build on supported macOS, Linux and Windows local filesystems. The repository already uses `node:sqlite`/`SyncDatabase` and Python `sqlite3`, but no shared fence path/connection is wired. Filesystem semantics on network shares, synchronized folders and removable/unmounted disks are not proven; refuse Laya publication there until separately verified.
- The system monitor currently supports Windows lock acquisition via `msvcrt`, and POSIX via `flock`; that lock is not the shared database protocol. Python monitor changes must be tested with actual two-process Node/Python contention on each claimed OS before registration.
- SSH is a separate machine and cannot participate in a laptop-local SQLite transaction. Remote project/agent/storage facts require an authenticated remote fence/read-revision RPC hosted beside the remote writer, with bounded availability and exact host identity; until implemented, those facts and dependent surfaces stay unavailable.
- External workspace-file writers (editors, Git, build tools, Syncthing), OS-level permission changes, external backup/restore, and arbitrary unmanaged disk users do not call Dobius hooks. Do not claim their content/state is fenced. Use immutable verified snapshots or exclude those facts; unavailable is the safe default.
- The external reservation ledger currently explicitly reports `participant-coverage-unverified`; RESEARCH found the only durable byte reservation ledger in C02 SQLite but could not prove every non-C02 disk consumer registers. Keep capacity and any derived storage recommendations unavailable.
- No production service, process, DB, root, workspace content, auth data, or provider was read. No Laya request, device, AWS, old Storage queue, Adam or Friday action occurred.

## Minimum acceptance before all-surface registration

1. Prove two independent processes (Node/Node, and Node/Python where applicable) contend on the exact same private authority DB: writer begun before file rename blocks publication; publication begun first blocks writer; bounded contention returns unavailable; no lost source writes. Include actual temporary SQLite/JSON stores, not the live authority DB.
2. Inject a writer commit between provider response and final publication; verify the published callback cannot append or cache. Race two authority writers, crash a child between JSON replacement and fence commit, then verify startup detects the source revision mismatch and remains unavailable until reconciliation.
3. Verify a `SafeJsonFile` process with a stale cache reloads under the fence and cannot overwrite another process's newer JSON. Verify `root-enrollment.lock`, monitor singleton lock and journal lock obey the specified order without deadlock; unknown/replaced lock identities stay fail-closed.
4. For jobs and capacity, test external-ledger insert after sample and between claim/start in the same SQLite transaction semantics; empty/unregistered producer sets remain unavailable. Include claim, permit, start receipt, heartbeat, cancellation, settlement, reservation release and recovery writers.
5. For agent-runtime, kill/restart a real temporary child process around publication and prove exact process identity/reconciliation; an event/timestamp alone is insufficient. If platform APIs cannot prove it, keep slot unavailable.
6. For data, use actual temporary roots and make external file writes during a paused scan. Either demonstrate immutable snapshot/content versioning or verify the data-content-based Laya surface refuses publication. Do not claim filesystem writers use the app fence.
7. Validate the same protocol on macOS/Linux/Windows local filesystems and explicitly refuse unsupported remote/network filesystems/SSH until an authenticated remote fence exists. ROOT must verify the expected participant roster and source owners independently; a source registry or empty row count is not completeness.
8. Decide journal atomicity: committed marker/filter or same SQLite transaction. Verify crash after JSONL append before fence commit cannot expose an uncommitted suggestion; verify cache hit and fresh result both use the fenced publication path.
