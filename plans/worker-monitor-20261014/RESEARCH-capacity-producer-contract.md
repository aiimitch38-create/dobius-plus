**Review status:** source-only contract, not implementation or live readiness.  
**Repository/branch:** `/Users/bayou/Projects (Code)/Dobius/dobius-plus`, `fix/channel-cost`.

## Finding

There is no existing trusted, complete inventory of all writers to a filesystem. C02 has a durable reservation for claimed cloud jobs, and the new non-C02 SQLite ledger can store owner-bound reservations, but it intentionally returns `participant-coverage-unverified`; it has no producer registry or proof that all other writers enrolled. An empty ledger therefore means only “no rows currently recorded.” It does not mean “no other operation can allocate bytes.”

A main-owned enrollment registry can prove that every **Dobius-managed producer in a deliberately bounded execution domain** participates. It cannot prove that every process on a shared OS volume participates. A machine-wide guarantee requires an isolated/quota-controlled filesystem or an explicit weaker contract: fresh OS free-space measurement plus reservations for known managed future intent, a conservative headroom floor, and refusal when any managed participant is unknown or stale. External processes can still consume the remaining bytes between checks.

The registry/config authorities in current source are not interchangeable:

- `cloud-worker-config-file.ts` and `cloud-worker-config-schema.ts` read a private, strict two-worker config. It can opt in the `hermes-1` and `hermes-2` worker slots and bind roots/worktrees/recipes, but a file-supplied producer ID or `enabled` flag alone is not proof that a writer is enrolled.
- `cloud-job-authority.ts` owns the single job database/service and main worker-host factory boundary. This is the appropriate main-process owner for constructing a producer registry and issuing producer-specific capabilities.
- `cloud-worker-external-reservations.ts` is a same-database persistence primitive with constructor-bound producer IDs and CAS revisions. Its snapshot is deliberately unavailable with `participant-coverage-unverified`; constructing a handle is not enrollment and the `CloudId` syntax check is not an allowlist.
- `cloud-worker-capacity-collector.ts` measures Linux `statfs` availability on a validated shared filesystem and validates repeated reservation snapshots. It has no producer discovery and cannot manufacture the `complete` proof.

## Trusted enrollment contract

The smallest safe authority is a main-owned registry constructed by the existing `CloudJobAuthority` composition, never by renderer/RPC input or by the worker-capacity JSON receipt. Use a fixed code-owned expected participant set for each enabled storage scope and typed factories that issue a capability only to a known owner. Private worker config selects whether the two configured worker slots are enabled; it cannot add arbitrary IDs to the expected set. Each producer factory is bound to `(deviceId, filesystemId, producerId, ownerGeneration)` and cannot impersonate another producer.

A scope can produce an available snapshot only if:

1. Every code-owned required participant for that scope has registered with the current authority generation, or has an explicit main-owned disabled/quiescent state that proves it cannot currently write there.
2. No participant is starting, recovering, draining, stale, failed, or unknown. Startup/recovery ambiguity keeps the snapshot unavailable.
3. Each active operation atomically reserves its future bytes before the first filesystem side effect in the same SQLite database. The operation carries a unique non-reusable reservation identity and exact owner/scope; reserve/release advances the same per-filesystem revision.
4. A reservation is released only after its operation is complete and any owned temporary/partial outputs are removed or terminally accounted for. Cancellation request alone is not release proof.
5. Every path is bound to the same stable filesystem identity measured by the collector. If producers target several filesystems, maintain one reservation total and sample per filesystem; never sum reservations across mounts or use one device-wide free-space scalar.
6. The C02 admission transaction reads C02 queued/running reservations and the non-C02 revision/total together, rejects if coverage/revision is unknown or changed, and writes its claim/permit atomically with that check. Sampling outside the transaction is advisory only.

A `complete` result must be constructed by the trusted registry after it checks the entire expected set; it must not be accepted from a producer, receipt, monitor, renderer or caller-provided boolean. Ledger rows show registered intent; registry membership plus current participant lifecycle establishes expected coverage. Unknown writers are not represented by zero.

## Reservation and headroom model

For a single validated filesystem, let `F` be current OS-available bytes (`bavail × block size` on the Linux collector), `C` the C02 future commitment, `E` the registered non-C02 future commitment, and `S` an operational safety reserve. Admit only if:

`F - C - E - S >= max(absoluteCriticalFloor, ceil(totalBytes × criticalFraction)) + requestedAdditionalBytes`.

The requested job’s minimum/estimate is reserved atomically before it starts and appears in exactly one authority: a cloud job uses its C02 row; a non-C02 operation uses its owner-bound external row. Never mirror one operation into both totals. OS `F` already reflects bytes allocated before the sample; do not add those bytes again as new intent. For an active operation, the ledger value must mean **remaining unmaterialized commitment**: as owner-attributed allocated output is confirmed, reduce that remaining amount because the allocation is now reflected in `F`. If progress cannot be measured safely, retaining the full reservation is a conservative over-reservation (safe but may deny work); it is not an exact-once accounting claim. Release the remainder only after completion/cleanup proof. Re-sample immediately before claim/start, but acknowledge that external writers can allocate between statfs and the transaction.

`S` must include a nonzero policy headroom for filesystem metadata, monitor/application state, logs/WAL, and ordinary unregistered system variation. A percentage/absolute floor protects against some races; it cannot convert a shared unquotaed machine into a hard reservation system. Prefer a dedicated volume with OS quota/isolation for a guarantee.

## Concrete smallest next slice

1. Keep the current external ledger snapshot unavailable. Add a main-owned `CapacityProducerRegistry` adjacent to the C05 worker-host composition (owner: ROOT; likely `cloud-job-authority.ts` plus a focused `cloud-worker-capacity-participants.ts` module). The registry owns an immutable required participant manifest and generation; only code-owned factories receive producer handles. Initial manifest should list C02 worker execution as already-covered-by-C02, plus each enabled, bounded Dobius-managed writer that can target the protected worker filesystem. Keep speech model, scrcpy, browser, native/SSH downloads and build tools either explicitly enrolled with enforced maxima or explicitly excluded from that filesystem. No “unknown => zero.”
2. Add a registration/reconciliation API that returns `unavailable` until every expected participant is registered or proven disabled/quiescent, and refuses an empty expected set as a proof of no writers. Couple it to worker authority startup/recovery/drain so configuration reload, worker restart, or unknown lifecycle invalidates the coverage generation synchronously.
3. Wire exactly one first producer cohort only after path containment is real: the two C02 worker slots and their bounded worktree/profile/state/artifact roots on one dedicated filesystem. Reuse C02 reservations for those job commitments; do not create duplicate external rows. If worker processes can write outside those roots or the same volume is shared with arbitrary processes, report “managed producer coverage only,” not hard capacity guarantee.
4. Add one non-C02 producer only after a concrete owner is selected (a bounded speech-model download is a reasonable isolated example). Require a pre-write max reservation, exact operation owner, progress-to-remaining-bytes accounting or a documented conservative full hold, and cleanup-bound release. Test disabled/missing/starting/recovering/stale participants, duplicate IDs, owner impersonation, multi-filesystem mismatch, crash/reopen retention, revision races and unknown-write denial.
5. Only then extend C02 claim and start-permit code to read external revision/total inside their existing `BEGIN IMMEDIATE` transaction using the existing caller-owned transaction read primitive. Test an insertion after sampling and between claim/start. This requires explicit ROOT assignment because claim/start/store ownership is separate.
