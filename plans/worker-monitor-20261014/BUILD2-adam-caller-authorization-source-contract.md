# ADAM control to Dobius execution: authenticated bridge boundary

Status: **source preflight only; no authenticated production ADAM-to-Dobius bridge exists.** ADAM remains an independent control service for planning, approval, and recovery decisions. Dobius main remains the laptop/VPS execution and local OS-cryptography layer. The earlier suggestion to make ADAM a Dobius-main-owned child is superseded and must not be used as the system ownership model.

## Current source facts

- ADAM is an independently launched service. `service/src/main.ts:7-17,38-52` constructs `AdamService`, chooses its data directory/port from its own process environment, starts it, and handles its own shutdown. No inspected Dobius main composition retains an ADAM child-process handle.
- Dobius reaches ADAM outbound through `dobius/src/main/adam-connection.ts:13-21,62-100`; source allows the configured local/default or tailnet endpoint and sends a bearer credential to ADAM. That is Dobius authenticating to ADAM, not ADAM authenticating to Dobius. No live remote deployment is inferred.
- Dobius runtime RPC authenticates possession of a same-user runtime bearer token (`runtime-rpc.ts:1000-1021`), records that token in private runtime metadata (`:1175-1183`), and uses a private Unix socket mode on Unix (`unix-socket-transport.ts:72-74`). `RpcContext.authenticatedLocalSocket` is only the generic local token result (`rpc/core.ts:45-56`). It does not attest an ADAM process, service instance, executable, or approval authority.
- `adam.submitCloudChild` rejects mobile/IPC contexts and requires local socket markers, but then supplies the constant principal `adam-parent-planner` (`rpc/methods/adam-cloud-child.ts:7-32`). Neither the Boolean nor the string authenticates ADAM. Do not add unseal to this generic RPC.
- The current main source composes ordinary cloud jobs and the outbound ADAM client (`main/index.ts:2131-38,2170-89`) and shuts these down (`:2382-2407`). It does not compose a reciprocal ADAM service principal/bridge. The new unsealer exists at `cloud-job-adam-intent-unsealer.ts:29-53,67-152`, validates the sealed envelope against a caller-supplied expected identity and decrypts in main, but exposes no caller authentication itself and is not wired into a production ADAM bridge. Its injected runtime seam is explicitly test/composition input, not a principal.
- ADAM's issue request has a bounded TTL and stable fields (`intent-contract.ts:7-32`). `issueGrantWithIntent` seals before transaction publication (`intent-publication.ts:32-78`), and `receipt-store.ts:57-101` atomically publishes binding plus intent after rechecking instance/parent state. Source search found only these implementation definitions for `issueGrantWithIntent`, not a production planner caller. ADAM's current HTTP routes authenticate a bearer token and expose consume/receipt routes (`runtime/service.ts:259-285`); no issue-grant planner route or Dobius execution bridge is present.
- Existing Dobius source has a useful bounded execution/recovery foundation: `cloud-job-submit-admission.ts:41-64` performs grant consumption, exact bound-child lookup on planner recovery, then atomic idempotent submission. `cloud-job-adam-client.ts:45-113` supports exact consumed-response replay after expiry and validates the full binding identity/digest. This is not caller authentication or an ADAM-side planner.
- The current installed receipt is `root-local-delivery.json#desktop_build20_delivery`: build 20 is installed, but `live_dispatch_ready` is false and `adam_bridge_enabled` is false. It states no real ADAM endpoint activation. The earlier build 17 sentence is stale and is retained only in history.

## Concrete bridge contract

**Authority split.** ADAM's production planner owns user-approved parent objective/version, project, context, stable intent ID, canonical child request/fingerprint, grant issuance, durable intent state, and decisions about whether to create or recover an execution. Dobius main owns the local OS encryption adapter, admission/workspace safety checks, child job execution, and durable execution result. The bridge carries approved bounded intent and result DTOs; it does not move planning or parent-state ownership into Dobius.

**Authenticate the service, not a caller claim.** Add a dedicated ADAM-control transport and principal registry in Dobius main, separate from the generic runtime RPC. A connection is admitted only after a platform-backed service identity check bound to an enrolled ADAM service identity and its current instance/connection generation. Caller parameters, a local-socket token/Boolean, user ID, endpoint, PID/path, executable hash, or injected callback alone cannot establish that identity. Main synchronously invalidates the principal generation on transport close, app shutdown, service restart/re-enrollment, or identity revocation; every async seal/unseal/admission path checks the same generation after awaits and before publishing results.

For a **local** service, use a dedicated OS-authenticated mechanism that can identify the service process, not just the same logged-in user: e.g. macOS XPC with audit-token/code-signing requirement; Linux Unix peer credentials under a dedicated service UID plus service-manager/executable identity; Windows named-pipe impersonation with an enrolled service SID. Unsupported or ambiguous platforms fail closed. These are requirements for implementation and platform tests; no such identity provider is present in current source. For a **remote** ADAM, require mutually authenticated TLS with an explicitly enrolled, rotatable/revocable ADAM service identity and a private listener. Existing local/tailnet URL allowlisting and the Dobius-to-ADAM bearer token do not provide this reverse authentication. Remote requests may use the laptop's OS crypto only by calling this authenticated local-main bridge; no key or safeStorage primitive leaves the device. Until each deployment has an actual supported principal provider, unseal and bridge admission remain disabled.

**Narrow operations and flow.** The dedicated protocol provides only (1) `sealApprovedIntent`, (2) `submitApprovedChild`, and (3) `recoverExactChild`, with strict versioned schemas, canonical digests, a 64 KiB maximum payload, bounded deadlines/concurrency, generic redacted failures, and content/capability-free logs. No generic RPC or caller-selected method is exposed.

1. An actual ADAM planner/approval action constructs the immutable tuple `intentId`, `bindingId`, `adamInstanceId`, `parentObjectiveId`, `parentObjectiveVersion`, `projectId`, `contextDigest`, `requestFingerprint`, `expiresAtMs`, and canonical child request/digest. It rechecks the same parent version/project and explicit approval immediately before issuance.
2. ADAM calls `CloudJobReceiptStore.issueGrantWithIntent` with a sealer callback to the authenticated Dobius main bridge. Dobius seals only the strict purpose envelope and returns ciphertext; ADAM then atomically persists binding+intent before publishing the grant. Capability bytes must not enter argv, logs, plaintext DB columns, runtime metadata, or renderer/CLI RPC.
3. ADAM sends the approved bounded job DTO through the authenticated bridge. Main checks the enrolled principal/instance generation and full tuple, verifies project/request fingerprint, performs fresh local admission, uses the existing ADAM consume/receipt client, and calls the existing bound submission path. Main returns only a bounded child identity/state/result receipt; ADAM alone updates parent state.
4. On restart, ADAM reads its durable original intent and submits `recoverExactChild` with the original sealed envelope and identity. Main unseals only for this exact identity, uses the existing ADAM exact-consumed-response replay, and performs `findAdamBoundChild` before any idempotent recovery write. Expiry blocks a new or previously unconsumed approval; it does not block an exact replay/lookup for an already-consumed original binding. No replacement grant or changed request is minted. If no exact consumed proof is available, return unavailable; never fall through to a new submission. Freshness gates new submissions, while the narrow old-intent reconciliation path is separately authorized and cannot create a different child.

A preferred integration keeps recovered capability bytes inside Dobius main: the authenticated recovery operation can unseal, replay the exact binding through the existing ADAM client, and return only the matched child DTO. If an implementation must return a grant to ADAM, it must be explicit, encrypted in transit, current-principal-only, and never logged/persisted beyond ADAM's existing protected durable model; do not add a generic decrypt endpoint.

## Smallest next implementation slice

1. **Dobius main:** a dedicated `adam-control-transport` plus OS identity provider/registry and lifecycle generation, composed/disposed from `main/index.ts`; no generic `adam.submitCloudChild` authorization reuse. Wire the already-owned sealer/unsealer only behind the new authenticated principal and strict operation schemas. Keep current unsealer owner responsible for its source freeze.
2. **ADAM service:** a narrow `service/src/adapters/dobius-execution.ts` client and a production planner/recovery caller under `service/src/dobius-cloud/` that uses the existing `issueGrantWithIntent` transaction. Register only the narrow call through the service's existing lifecycle in `service/src/runtime/service.ts`; keep `service/src/main.ts` independently owned by ADAM.
3. **Proof before enablement:** deterministic injected-identity tests for rejection of same-user/unregistered/stale principals, instance restart/revocation during every await, oversized/malformed DTOs, no secret/log/argv persistence, approved new submission, expired-unconsumed refusal, and expired exact-consumed lookup/recovery with no new grant. Add per-platform OS-identity integration tests and a local cross-app fixture before enabling any production bridge. Remote mTLS enrollment/rotation needs its own integration fixture.

No actual service process identity proof, production planner caller, reciprocal transport, keychain access, ADAM database access, or runtime activation was performed here. The crypto module alone is not authorization. Tests with injected principals prove only a test seam. Keep the bridge and unsealer unavailable until the service principal and full ADAM caller path pass independent review.
