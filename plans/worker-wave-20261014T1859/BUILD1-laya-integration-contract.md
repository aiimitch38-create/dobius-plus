# BUILD1 Laya production authority epoch integration contract

Recorded 2026-10-14. This is a read-only integration design. No source module was changed and no production composition, provider, credential, or service was activated.

## Current boundary and evidence

The accepted `build1.json:c08_c09_laya_advisory_composition` freeze is `64e28b6634c018c5cc16d7b0a1a87500c9083157a795bdc30f38c1ab8b7e477a`; it is explicitly `SOURCE_FROZEN_FOR_INDEPENDENT_REVIEW; NOT_WIRED_OR_DEPLOYED`. Its factory accepts injected authority, deployment-gate, journal, and one synchronous epoch reader, and passes that same reader to `LayaAdvisoryService` and `LayaHttpDecisionProvider`. Provider creation remains opt-in and requires trusted receipt and authorization callbacks. ROOT's `root-local-delivery.json` independently records `laya_composition_current_source.status=RESEARCH_PASS_NODE24_58_SOURCE_ONLY`, `providerActivated=false`, and acceptance open for production epoch adapter, provider, and quality evaluation.

`laya-authority-epoch.ts` is only a strict safe-integer reader/check plus a random HMAC key/revision digest helper. It does not own versions or subscribe to writers. The service captures the ticket before asynchronous work, rereads the authority and deployment gate after provider completion, and checks the epoch synchronously immediately before persistence/cache publication. The provider also checks the epoch around awaited receipt, authorization, health, and decision requests. Therefore every state change that can invalidate a snapshot must synchronously advance/invalidate the same reader before the changed state becomes visible; asynchronous notifications after commit leave a stale-publication window.

The six schema surfaces in `shared/laya-advisory.ts` are semantic projections, not six existing shared tables or one existing production authority: `job-routing`, `kanban`, `agents`, `data`, `storage`, `verification`. The source does not contain a production `LayaAuthorityReader`, production epoch owner, or composition wiring. No all-surface consistency claim can be made today.

## Required composition and writer contract

Proposed integration files, after this contract is accepted:

- `dobius/src/main/decisions/laya-production-authority-epoch.ts` — main-process owner of one monotonic safe-integer generation, with a synchronous `current(): number | null` reader and synchronous `beforeCommit(domains, entityIds)` invalidation API. Reader returns unavailable while the owner is invalid, a writer is in a commit window, a required producer is not registered, or the generation cannot advance safely; it never falls back to a constant or wall clock.
- `dobius/src/main/decisions/laya-production-authority-epoch.test.ts` — real temporary SQLite/JSON/filesystem fixtures and injected barriers for all supported writer paths and races.
- `dobius/src/main/decisions/laya-production-authority.ts` — a main-only snapshot assembler that reads the six actual authority adapters, validates schema and subject binding, and samples the shared epoch synchronously before and after assembly. It must return unavailable if any required source is absent, stale, inconsistent, or changes during collection.
- `dobius/src/main/decisions/laya-production-authority.test.ts` — cross-source snapshot consistency and asynchronous stale-result publication races.
- Existing writer files to adapt only after exact ownership and writer inventory are confirmed: `automations/cloud-jobs/cloud-job-catalog.ts`, `automations/cloud-jobs/cloud-worker-attempt-lifecycle.ts` plus any transaction writers found by call graph; `vertex/vertex-task-store.ts` and dispatch recovery writers; `agents/agents-store.ts` plus runtime heartbeat/session writers; `storage/data-catalog/root-enrollment-store.ts`, catalog preview lifecycle and system-monitor snapshot producer; cloud capacity reservation transaction writers; and the trusted verification receipt producer. The corresponding owner must provide a synchronous pre-visible-commit callback and identify the durable revision/lock that serializes it.
- ROOT-owned production composition path (currently absent from the accepted factory packet) must construct exactly one authority epoch/assembler and pass the same reader instance to both service and HTTP provider. This task does not select or edit ROOT-owned composition files.

A plain increment after each write is insufficient. For sync SQLite/JSON commits, invalidate synchronously before the commit call and leave the epoch advanced even on rollback; stale cached replies then fail closed. For mutations with awaits (directory chooser, filesystem scan, monitor collection, worker RPC), reserve/invalidate before the first await, then revalidate identities/lease and invalidate again at the final synchronous commit boundary. Readers must refuse during in-progress mutation windows. Any mutation path that can bypass the callback, including direct store access, recovery, startup reconciliation, cross-process writer, or background script replacement, blocks production reader registration. Entity-level source revisions should be retained in snapshots for audit and exact subject binding; one scalar epoch is the cross-source invalidation fence, not a fabricated replacement for source revisions.

The current source files show useful serialization primitives but no universal revision generator: SQLite mutations use synchronous `BEGIN IMMEDIATE`; cloud jobs carry job versions/event sequences and durable attempt/permit receipts; catalog roots use a cross-process exclusive lock and per-root UUID generation; catalog preview has an in-memory epoch; `SafeJsonFile` uses atomic persistence without a shared cross-file version; Vertex task ordering/status is persisted but no Laya-facing revision was found; system monitor samples have freshness time but no monotonic content revision. Reuse these actual transaction/lock/entity versions, add callback coverage at their owning boundaries, and do not claim they jointly provide a consistent epoch until every writer participates.

## Race tests required before source acceptance

1. Pause a provider response after a real job/attempt snapshot; commit a job cancel, project/root change, permit revoke, or worker settle through the production writer; release provider. Service must return unavailable and must not journal/cache a suggestion.
2. Repeat with a Vertex task move/completion and with dispatch claim recovery; include direct internal store call so service-only hooks cannot pass.
3. Pause `agents` snapshot after configuration read; update profile/tool grants, then heartbeat/process identity/session lease; prove each invalidates and stale suggestion never publishes.
4. Pause data catalog/root/file scan, then revoke root/device preview grant, replace root incarnation, change relevant file evidence, and revoke/expire the preview lease; no stale result may publish.
5. Pause storage snapshot/capacity read; publish a monitor sample/config change and commit/release an external or C02 reservation; reject the old snapshot. Exercise concurrent writers and cross-process lock/transaction paths.
6. Replace/revoke a verification receipt or deployment receipt after the initial read and while HTTP is awaiting; provider/service must reject before outbound decision fetch where applicable and before journal/cache commit.
7. Race two writers across sources and prove snapshots cannot observe a partially updated multi-authority state. Also inject a writer that omits registration and prove the epoch becomes unavailable rather than silently retaining the prior value.
8. Force generation exhaustion, reader throw, malformed/missing source revision, lock contention, rollback, and stale external source version. All must fail closed; no timestamp-only or constant epoch test is acceptable.

Use real temporary stores/files and actual writer APIs, with deterministic deferred promises. Synthetic callback-only counters are useful unit tests but do not prove production writer coverage.

## Smallest safe source slice and remaining gates

The smallest useful implementation slice is a fail-closed coordinator plus complete callback coverage for one coherent, actually authoritative slice (cloud jobs/project/attempt/reservation and its source revision), backed by SQLite transaction fixtures and a service stale-publication race. It must remain unavailable for all six surfaces until each required producer/writer is registered. Do not wire a partial scalar as if it covered all surfaces. Next add roots/storage because their existing lock and external reservation semantics are necessary to job-routing and storage facts. Then add Vertex, agents/live session facts, data/preview, and verification only with owners for their true producers. Finally ROOT may wire the fully registered reader into the accepted composition.

Inputs still missing for any production claim: complete writer call graphs/owners for agent runtime, monitor snapshot producer, external reservation authority, data pins/active leases/remote verification, and verification receipts; a trusted immutable accepted human-evaluation report for the exact source/checkpoint/model; provider endpoint and authorization source (values must remain in the approved secret manager and are not requested/read here); pinned deployment receipt/checkpoint health; ROOT-owned production composition; and independent source review. `root-local-delivery.json` still says no Laya activation and quality evaluation is open. No live inference substitutes for those evaluation gates. Source acceptance will not establish packaging, installation, service activation, production consistency, or model quality.
