Read-only source and delivery-state map, 2026-10-14. This is an integration contract, not a dispatch-readiness or live-enrollment claim.

## Concrete source path

`main/index.ts` constructs the callback `workerHostFactory(context)`, which passes the authority-owned `baseDirectory` and `deviceId` to `createPrivateCloudWorkerCapacityReader` and then `createConfiguredCloudWorkerHostFactory`. `cloud-job-authority.ts` creates one `CloudJobStore` at `<baseDirectory>/jobs.sqlite`, persists dispatch disabled at open, registers the authorized projects, and attaches the optional worker host through `CloudJobService`. `CloudJobService` attaches the host to that same store and refuses to close it until worker shutdown reports a proven drain.

On first store attachment, `cloud-worker-bootstrap.ts` reads private `workers.json`, validates its captured generation and authority, checks registered projects and physical prerequisites, and binds the resulting factory to the supplied store. It creates exactly two `WorkstationWorker` objects from the two validated enrollments. Each is constructed with a `CloudWorkerQueuePort` created by the host runtime for that same store. `CloudWorkerHostRuntime.start()` performs recovery with dispatch closed before periodic polling; readiness additionally requires current authority/capacity, recovered journals, and no ambiguous slot. A separate persisted dispatch switch gates actual claims.

For a claim, `CloudWorkerQueuePort.claim()` reads current capacity and calls transactional `CloudJobStore.claim()` with server-enrolled worker identity, assignments, caps, and minimum working bytes. Before spawn, `authorizeStart()` revalidates the exact lease/assignment/root and fresh capacity, then transactionally records a short-lived permit against current persisted reservations. `WorkstationWorker.runClaim()` obtains that permit before writing launch intent or spawning only the registered executable/arguments. It records the process identity, acknowledges the started receipt, and then observes and settles the attempt. Reconciliation and stop proof remain bound to the exact worker, attempt, lease token, PID/start identity, and process group; ambiguous cleanup retains the reservation and worker fence.

## Two-slot and profile rules

Carson's requested unattended roster is exactly two Hermes agents: Adam and Friday; do not provision two additional agents. The current source schema does not name profiles Adam/Friday: it requires the two service profile slots `hermes-1` and `hermes-2`, each exactly once, with distinct worker IDs, homes, and worktrees, and each assignment linked to an approved project/root/worktree/recipe/capability. The trusted enrollment should explicitly map the Adam and Friday worker identities onto those two existing slots. Do not reject those worker identities by name. The isolation rule is about concurrent ownership: neither slot may run headless work through a profile instance that is currently in use by an interactive session. Bootstrap rejects noncanonical, unsafe, aliased, or improperly separated paths before creating worker state. Execution uses the selected profile home as `HOME` and `HERMES_HOME`; no credential value is passed through the worker environment. The current config's `authVerified`, `runtimeVerified`, and `credentialRef` fields are enrollment claims, not independent proof: the inspected execution path has no credential resolver or live Hermes authentication/runtime verifier.

The worker's private journal distinguishes fresh/idle, an exact active lease, and unknown. Unknown journal, process, host lease, or stop state is fail-closed. `safeEnvironment()` is limited to the approved path/home/language variables, process launch is POSIX-only, and process cleanup is tied to recorded process identity rather than broad name matching.

## Capacity semantics and blocking input

`CloudWorkerCapacitySample.freeBytes` is disk headroom, not RAM; there is no free-RAM field. `WorkerCaps.memoryBytes` is a per-job cap and is not available-memory telemetry. The admission calculation is:

`freeBytes - externalReservedBytes - current persisted C02 queue reservations - safetyBytes`

The queue's transactional SQLite reservation is counted once at claim and rechecked against current persisted reservations at start permit. Already allocated files are reflected in filesystem free space and must not be subtracted again. `externalReservedBytes` means complete, authenticated non-C02 commitments for the same filesystem that are not already reflected in the sampled free space.

`createCloudWorkerCapacityCollector()` now provides a Linux-only, descriptor-bound statfs reader and requires two matching, fresh, complete snapshots from an injected non-C02 reservation authority. Its tests cover synthetic filesystem identity, stale/changed reservation snapshots, descriptor/path replacement, and overflow; ROOT has recorded an isolated Linux run of its 8-test suite as passing. However, no implementation currently supplies that complete external-reservation authority, the collector is not wired into bootstrap, and no capacity receipt should be emitted while that authority is absent. The existing private reader accepts a service-owned `worker-capacity.json` only when strictly shaped, device-bound, and at most 5 seconds old; it is a reader, not a producer.

## Smallest next implementation slice

First add one narrow service-owned reservation-authority adapter which can return a synchronous snapshot with all of: `deviceId`, verified filesystem identity, `coverage: "all_non_c02_reservations"`, `complete: true`, current matching revision, total outstanding non-C02 bytes, and sample time no more than 5 seconds old. Its backing owner must enumerate every non-C02 reservation source that can consume the worker filesystem; if any source cannot be enumerated or bound to that filesystem, it returns unavailable. It must define whether a commitment is already reflected in `statfs` and exclude those bytes from the external total. No current file implements or authoritatively supplies this contract, so ROOT must identify the actual reservation owner before implementation; a synthetic zero-valued test reader is not an acceptable production substitute.

Once that owner is identified, the smallest source change is to wire its trusted reader into the existing injected `createCloudWorkerCapacityCollector({deviceId, paths, safetyBytes, readExternalReservations})`, and pass that live synchronous collector as the existing `readCapacity` callback through the current `workerHostFactory` in `main/index.ts`. Keep the current `CloudJobStore`, `CloudWorkerQueuePort`, `CloudWorkerHostRuntime`, and two enrolled `WorkstationWorker`s as the sole claim/start/settlement path. Do not add another queue, dispatcher, mutable capacity receipt, or RPC for local workers. This wiring should remain readiness-false until the private two-profile enrollment, worker paths, executable/runtime verification, and reservation authority are all valid.

Acceptance tests for the adapter/wiring should prove: (1) an incomplete, stale, wrong-device, wrong-filesystem, changed-revision, throwing, or unavailable external source refuses readiness and claims; (2) non-C02 bytes are subtracted once while C02 persisted bytes are added once at claim and permit, including two-worker overbooking; (3) source replacement during sampling is refused; (4) the strict `workers.json` exactly-two-Hermes slot binding passes, allows exactly the Adam and Friday worker identities without adding agents, rejects duplicate/aliased homes or worktrees, and refuses concurrent reuse of a profile instance held by an interactive session; (5) recovery precedes any claim and the same store/QueuePort instances reach both real worker objects; (6) permit, process identity, settlement, cancellation, stop receipt, and reservation retention survive reopen and ambiguous cleanup. Existing synthetic store/adapter/runtime and actual-process fixture tests cover much of (2), (5), and (6); they do not establish service-owned production enrollment, actual Hermes auth, or remote deployment.
