# Repair plan: phone multi-terminal flicker and input loss

## Diagnosis

The current evidence confirms the terminal-only flicker symptom, WebView process-termination events in Metro logs, and an overlapping transport interruption. It also reproduces a source-level live-input loss: the mirror advances its local sent-text baseline before the RPC succeeds, and later deltas are sent even after a prior delta failed. In the source model, if delta `a` returns false and reconnect occurs before the next edit, typing `ab` sends only `b`. No keystroke-level log proves that exact ordering occurred on the phone. The trigger for WebView process termination and its relation to input loss remain unproven.

The shared Metro log at `/Volumes/Storage/dev/metro.log` records seven `Terminal WebView content process ended` events and seven `Webview Process Terminated` warnings at lines 1424–1438. A `foreground — probing live connection` message immediately precedes them. In the same log sequence, the RPC client reports a WebSocket close with code 1001, enters reconnecting, and logs `sendEncrypted FAILED — channel not ready` at lines 1440–1460. Earlier in this log are seven Metro startup markers (lines 3–637); the currently running Expo process has been alive since 2026-10-08 01:36, so those earlier starts do not explain the later clustered renderer/transport failure.

Metro currently serves `/Volumes/Storage/dev/dobius/dobius/mobile` from `feat/mobile-desktop-screen` at `fce5fca4`. That is not this isolated repair lane at `131327ee`. The input handler blocks in the session route match between the two worktrees, while `TerminalWebView.tsx`, `terminal-webview-html.ts`, and `rpc-client.ts` differ. The live renderer therefore does not include this lane's measurement-correlation and keyboard-metric deduplication commits. `TerminalPaneView.tsx` is identical and intentionally keeps inactive terminal WebViews mounted with opacity zero. This is a possible resource-pressure contributor, not a proven trigger.

The phone's text keyboard uses native React Native `TextInput` and `terminal.send`; it does not depend on xterm receiving keystrokes. `rpc-client.ts` waits for a connection before a request, then rejects if the encrypted channel is not ready; input is deliberately not replayed across reconnects. `use-terminal-live-pending-input-flush.ts` updates `sentLiveInputTextRef` before awaiting the send and `terminal-live-pending-flush-state.ts` deliberately runs the next dependent delta after a prior false result, despite its comment recognizing that skipping a delta desynchronizes later edits. Once the channel returns, later deltas omit the failed prefix. The user still sees the text field change locally, but the terminal misses bytes; Enter can then clear the field while submitting only a carriage return. The server input handler accepts mobile sends and takes the floor after the write; current source inspection does not show a general mobile ownership rejection for ordinary `terminal.send`.

Later direct user clarification narrows the display symptom: flicker occurs only in terminal views. Two terminal views are currently fine, but the identities are not stable: closing and reopening the phone app changes which terminals flicker, and the manager terminal was affected earlier. This supersedes the initial manager-only flicker report as the current symptom boundary. The rotating set makes session/WebView lifecycle and restoration order a stronger investigation target than a fixed terminal's content, but does not prove a mechanism or link it to input loss. No per-session lifecycle trace or physical cause has been established.

The current Metro log cannot attribute the seven process exits to terminal identities or say whether each WebView was active, and it does not align them with per-view load/ready generations. The isolated lane now adds development-only WebView lifecycle events for active-state changes, load start/ready, reload request, native load errors, and render/content process loss. Each event carries a stable short hash of the terminal handle, active state, generation, wall-clock time, and elapsed time since the previous event; raw handles and terminal input/output are excluded. This is diagnostic instrumentation only and does not recover or change WebView ownership. It needs a later integrated phone reproduction to establish whether these transitions line up with the rotating flicker set.

A second source-level input-loss case is reproduced across terminal selection: while terminal A's send promise is unresolved, switching to terminal B and typing queues B's independent input behind A. If A then returns false, the shared promise chain suppresses B as though it depended on A's delta. This fits the user's multi-terminal input symptom, but physical timing has not been captured. The hook now detaches the old pending chain only when the active handle changes; it still serializes dependent deltas for the same handle and preserves the failed-send latch there. A deferred-send regression and the actual-hook Node harness verify that A's late failure does not prevent B's send.

Source inspection of WebView recovery shows that a content-process end reports a native engine error; it does not itself reinitialize the terminal. After a subsequent `web-ready`, the session detects an already-ready initialized handle, unsubscribes it, clears its initialized marker, and resubscribes the active terminal so the new WebView generation receives a fresh snapshot. This is a plausible redraw/recovery boundary for the terminal-only flicker, especially with the rotating affected set, but no physical lifecycle trace currently shows that it is the flicker trigger. Existing development diagnostics are intended to correlate that boundary in a later phone reproduction.

The installed Metro supervisor is another separate uncertainty: the running copy under `~/Library/Application Support/dobius-mobile/metro-supervisor.mjs` predates the shared checkout's modified script. The installed copy treats any `/status` request exception as unhealthy, while the modified checkout treats a timeout during bundling as busy. The log contains multiple startup markers, but lacks timestamps and reason codes, and the current Metro child has been up for more than twelve hours. This does not establish a supervisor restart during the reported failure.

## Repair and verification

The queue now propagates a failed or throwing send as a failed chain result and does not execute dependent deltas. The input hook marks the mirror uncertain after a failed send, retains the user's draft, blocks later deltas, Enter, and accessory/control sends, and clears that state only when the user explicitly empties the field or resets the input session. A deferred-send regression caught the clear-before-failure race: if the user empties the field before a pending RPC resolves false, the failure completion now resets that still-empty session and fences off callbacks from its old generation. Suppressed queued deltas are detached only after the failed send settles, so fresh input starts an independent chain without replaying uncertain bytes. The session route shows a throttled, neutral warning when the send is unconfirmed: “Input was not confirmed. Check the terminal before retrying.”

Regression coverage includes a rejected first delta followed by more typing and submit (no later delta or carriage return; complete draft remains visible), Backspace and accessory paste after failure, explicit clear followed by a fresh send, clear while an RPC is pending followed by failure and fresh input, queue suppression after a false or throwing prior send, direct switching while the old handle's send remains pending, and leaving terminal mode before selecting another handle. The hook test fixture keeps its terminal-handle value and ref synchronized, matching the session route. A reusable React Test Renderer harness at `/tmp/dobius-phone-live-input-harness.mjs` executes the actual hook and queue under Node 24; after the handle-switch fix it passes failure suppression, draft retention, clear-race recovery, fresh-session recovery, and independent sending after terminal-mode navigation.
